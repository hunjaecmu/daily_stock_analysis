# 종목 선별 엔진

DSA는 종목 선별(스크리닝) 기능을 본 프로젝트의 일부로 관리합니다. 구현은 [AlphaSift](https://github.com/ZhuLinsen/alphasift)의 커밋 [`9f522747caafd3c0b1ddb7e14d5cf44c8580b6cf`](https://github.com/ZhuLinsen/alphasift/commit/9f522747caafd3c0b1ddb7e14d5cf44c8580b6cf)를 참고했으며, Apache License 2.0에 따라 수정해 배포합니다. 파생 파일에는 출처 머리말이 남아 있고, 라이선스는 `src/services/screening/LICENSE`, 제3자 고지는 루트 폴더의 `THIRD_PARTY_NOTICES.md`에 있습니다.

## 코드 경계

- `src/services/screening/`: 스냅샷, 일봉, 전략 불러오기, 필터링, 점수 계산, 위험, LLM 재정렬, 테마(핫스팟) 구현.
- `src/services/screening/strategies/`: DSA 버전과 함께 배포되는 전략 YAML.
- `src/services/screening/pipeline.py`: 선별 흐름의 직접 진입점.
- `src/services/screening_service.py`: DSA 업무 흐름 구성. pipeline을 직접 호출하며 설정, 데이터 소스 컨텍스트, 응답 정규화, 캐시, 오류 대응을 맡습니다.
- `src/storage.py`: DSA의 기존 SQLAlchemy/SQLite 기반을 써서 완료된 선별 실행을 저장합니다. 별도의 파일 데이터베이스를 만들지 않습니다.
- `api/v1/endpoints/screening.py`: `/api/v1/screening` API.
- `apps/dsa-web/src/api/screening.ts`와 `StockScreeningPage.tsx`: Web 호출과 화면 표시.

서비스 계층은 `screening.pipeline`, `screening.strategy`, `screening.hotspot`을 정적으로 호출합니다. 핵심 로직은 모듈 이름 탐색, 동적 어댑터, 여러 갈래의 라우팅으로 나뉘지 않으므로, 코드 구조, 오류 경계, 패키징 대상은 모두 본 프로젝트가 직접 정합니다.

## 설정

기본값은 꺼짐입니다.

```dotenv
SCREENING_ENABLED=false
```

Web의 "기본 설정" 화면에 "종목 선별" 스위치가 있습니다. 메뉴에는 "종목 선별" 진입점이 항상 남아 있습니다. 꺼져 있으면 페이지에 켜는 방법 안내가 나오고, 선별 API는 업무 요청을 계속 거부합니다. 상태를 불러오는 동안에는 "꺼짐"을 표시하거나 켜기 동작을 허용하지 않습니다. 상태 요청이 실패하면 "상태 알 수 없음"과 다시 시도 버튼을 보여 주며, 네트워크 실패를 설정 꺼짐으로 다루지 않습니다. 켜져 있고 엔진을 쓸 수 있다는 것이 확인된 뒤에만 전략과 테마 작업을 실행할 수 있습니다. 진입점을 열거나 상태를 다시 확인해도 설정을 자동으로 바꾸거나 선별 작업을 제출하지 않습니다.

자주 쓰는 선택 항목:

```dotenv
SCREENING_DATA_DIR=data/screening
SCREENING_SNAPSHOT_CACHE_TTL_SEC=300
SCREENING_SOURCE_CALL_TIMEOUT_SEC=
SCREENING_HOTSPOT_CALL_TIMEOUT_SEC=8
SCREENING_HOTSPOT_SEARCH_TIMEOUT_SEC=12
SCREENING_SNAPSHOT_CALL_TIMEOUT_SEC=60
SCREENING_DAILY_CALL_TIMEOUT_SEC=20
SCREENING_EASTMONEY_MIN_INTERVAL_SEC=1.0
SCREENING_EASTMONEY_JITTER_SEC=0.3
```

경로, 캐시, 제한 시간, 요청 속도 제한 항목은 종목 선별 흐름에만 영향을 줍니다. `SCREENING_SNAPSHOT_CACHE_TTL_SEC`는 기본 300초이며, `0`으로 두면 최근 스냅샷 재사용을 끕니다. `SCREENING_HOTSPOT_CALL_TIMEOUT_SEC`의 양수 값은 기본 테마 provider가 한 번 호출할 때 업종, 구성 종목, 직접 상세 조회 fallback에 쓸 수 있는 전체 시간 예산입니다. 이후 fallback과 병렬 구성 종목 소스는 같은 마감 시각을 함께 쓰며, 남은 시간을 종료 가능한 AkShare 하위 프로세스와 HTTP 소켓에 넘깁니다. `0/off/disabled`로 두면 이 전체 예산만 꺼지고, 각 실제 데이터 소스의 개별 강제 제한 시간은 그대로 남습니다. `SCREENING_HOTSPOT_SEARCH_TIMEOUT_SEC`는 사용자가 직접 실행한 뉴스 검색의 처음부터 끝까지의 마감 시간입니다. 캐시 소유자 대기, 재경쟁, provider 하위 프로세스가 같은 절대 마감 시각을 함께 씁니다. `0/off/disabled`로 두면 무한정 기다리지 않고 안전한 기본값 12초로 돌아갑니다. 전체 예시는 `.env.example`을 기준으로 하세요.

## API 계약

| 경로 | 메서드 | 동작 |
| --- | --- | --- |
| `/api/v1/screening/status` | GET | 스위치, 엔진 상태, 계약 버전, 참고 프로젝트, 데이터 소스 상태 정보를 반환 |
| `/api/v1/screening/strategies` | GET | 선별 전략을 반환 |
| `/api/v1/screening/hotspots` | GET | 캐시를 읽거나, 명시적으로 새로고침해 테마 목록을 반환 |
| `/api/v1/screening/hotspots/{topic}` | GET | 테마의 흐름, 구성 종목, 핵심 종목을 반환. `include_search=true`이면 필요할 때 최근 뉴스를 검색 |
| `/api/v1/screening/screen/check` | POST | 호출하는 쪽이 넘긴 스냅샷 한 건으로 전략의 필수 필터 조건을 하나씩 검사. 시세를 가져오지 않음 |
| `/api/v1/screening/screen` | POST | 종목 선별을 동기로 실행. 익명 `variant_seed`를 넘기면 실행마다 범위가 정해진, 점수가 비슷한 후보 조합을 만들 수 있음 |
| `/api/v1/screening/screen/tasks` | POST | 백그라운드 선별 작업을 제출. 요청 필드는 동기 엔드포인트와 같음 |
| `/api/v1/screening/screen/tasks/{task_id}` | GET | 작업 진행 상황, 오류, 최종 결과를 조회 |
| `/api/v1/screening/history` | GET | 전략, 시장별로 최근 완료된 선별 실행 요약을 조회 |
| `/api/v1/screening/history/{run_id}` | GET | 저장된 선별 결과 전체 한 건을 읽음 |
| `/api/v1/screening/source-history` | GET | 과거 실행에서 스냅샷 소스의 적중, 오류, 기능 저하 횟수를 집계 |

백그라운드 작업은 `report_type=screening_screen`을 씁니다. Web은 진행 중인 작업 ID를 저장해 두었다가 페이지가 다시 열리면 계속 조회합니다. 작업 상태는 전체 시장 스냅샷, 후보 컨텍스트, LLM 재정렬, 최종 점수 계산, 뉴스·이벤트 보강 같은 단계를 각각 알려 줍니다. 완료된 결과는 DSA 데이터베이스에도 기록되므로, 서비스를 다시 시작한 뒤에도 `run_id`로 조회할 수 있습니다. 새로 실행한 동기/백그라운드 응답과 과거 상세 기록에는 `strategy_version`, `strategy_category`, `effective_factor_weights`가 남아, 실행 당시의 전략 버전, 분류, 실제 정규화된 팩터 가중치를 기록합니다. 예전 기록은 채워 넣지 않으며, 업그레이드된 전략 파일을 근거로 과거 기록을 고치지도 않습니다.

## 단일 종목 조건 검사(스냅샷 제공)

스냅샷이나 일봉 필수 필터 뒤에 후보가 하나도 남지 않은 실행도, 결과가 비어 있지 않은 경우와 똑같이 그 실행 전략의 정규화된 팩터 가중치를 남깁니다. 가중치는 실제로 실행한 전략이 파이프라인 출구에서 만들며, 서비스 응답과 과거 기록은 빠진 가중치를 채우려고 전략 폴더를 다시 읽지 않습니다. 이 메타데이터는 선별 설정을 기록할 뿐, 탈락한 후보까지 점수 계산을 마쳤다는 뜻은 아닙니다.

`POST /api/v1/screening/screen/check`는 스크립트/API 클라이언트가 임의의 스냅샷 한 건이 왜 전략의 필수 필터를 통과했는지 또는 통과하지 못했는지 설명받을 수 있게 합니다. `SCREENING_ENABLED`를 켜야 하며, 기존 선별 엔드포인트와 같은 관리자 인증 미들웨어를 씁니다. 인증을 켰을 때 유효한 세션이 없으면 `401`을 반환합니다. 전략 ID는 현재 켜져 있는 전략 폴더에서 찾으며, `market`(`cn`/`us`)이 해당 전략의 `market_scope` 안에 있는지 검사합니다.

```json
{
  "strategy": "dual_low",
  "market": "cn",
  "snapshot": {
    "code": "600000", "name": "Example", "price": 10,
    "amount": 100000000, "total_mv": 10000000000,
    "pe_ratio": 8, "pb_ratio": 1, "change_pct": 0
  }
}
```

- `strategy`, `strategy_version`, `market`, `provenance: "supplied_snapshot"`, 전체 `passed`, `checks`를 반환합니다. 각 항목에는 `filter`, 표준 `field`, 실제로 일치한 `source_field`, `threshold`, `current_value`, `status`(`pass`/`fail`/`missing`), `passed`(불리언 또는 `null`)가 들어 있습니다. `missing_reason`은 열 없음, 빈 값, 잘못된 숫자/텍스트, 유한하지 않은 값을 구분합니다
- 켜져 있는 모든 필수 필터 조건은 설정 모델의 필드 순서대로 각각 실행되며, 첫 항목이 실패해도 나머지를 계속 검사합니다. 기존 필터 판정 함수를 그대로 씁니다. 숫자의 위아래 경계값은 포함되며, `0` 기준값도 유효합니다. 비어 있는 허용 목록과 꺼진 불리언 조건은 반환하지 않습니다
- 열 없음, `null`, 빈 텍스트, 해석할 수 없는 숫자, 유한하지 않은 숫자는 `missing`으로 출력하며 `current_value`/`passed`는 `null`입니다. 값이 없는 것은 통과가 아닙니다. 전체 `passed`는 모든 조건을 통과했을 때만 `true`입니다(켜진 조건이 없으면 `true`). 이것은 진단용 엔드포인트가 쓸 수 없는 데이터에 붙이는 보수적인 "알 수 없음" 표시입니다. 기존 파이프라인은 이름이 비어 있어도 ST(특별 관리 종목) 검사를 통과시키거나 양의 무한대를 숫자 하한 검사에서 통과시킬 수 있지만, 이 엔드포인트는 여전히 `missing`을 반환합니다. 기존 파이프라인 동작은 바꾸지 않습니다
- 입력은 필드 1–64개의 평평한 JSON 객체여야 합니다. 키 길이는 1–64자, 텍스트 값은 최대 256자입니다. 중첩된 값이나 유한 부동소수점 범위를 넘는 정수는 범위가 정해진 `422`를 반환합니다. 기존 표준 필드/중국어 별칭과 이미 정규화된 단위를 쓰며, 통화나 백분율 변환은 하지 않습니다. 표준 이름과 별칭을 함께 주면 표준 이름이 우선합니다
- 일봉 조건은 제공된 값을 그대로 쓰며, 없으면 `missing`입니다. 따로 계산하거나 가져오지 않습니다. 응답에는 실시간 여부, 시각, 데이터 소스 신뢰도에 관한 보장이 없습니다. 종목 코드와 시장 소속은 호출하는 쪽이 책임지며, 이 결과를 검증된 증권 정보나 실시간 선별 결과로 여기면 안 됩니다
- 점수 계산, 순위 결정, LLM 호출, 실행 기록 저장, 매매를 하지 않습니다. 기존 동기/백그라운드 선별, 단계별 탈락 통계, Web 화면은 원래 동작을 유지합니다. 이 작은 엔드포인트에는 아직 Web UI가 없습니다

이 동작은 [Koyfin Check Ticker](https://www.koyfin.com/help/release-notes/check-ticker/)의 조건별 값과 통과/실패 표시 방식을 참고했으며, 설명 방식만 빌렸을 뿐 그 데이터나 서비스는 쓰지 않습니다.

## 핵심 흐름

```text
전략 불러오기
  -> 전체 시장 스냅샷과 필드 표준화
  -> 필수 필터
  -> 팩터 점수 계산과 위험 조정
  -> 범위가 정해진 후보의 시세/기본적 분석/뉴스·이벤트 컨텍스트 보충
  -> LLM 재정렬(실패 시 기능을 낮춰 계속)
  -> 위험/포트폴리오 제약과 비슷한 점수 후보 교체
  -> 상위 후보의 DSA 시세/기본적 분석/뉴스 보강
  -> API 정규화 응답과 DSA 데이터베이스 저장
  -> 사용자가 필요할 때 DSA 개별 종목 심층 분석으로 이동
```

- 전체 시장 스냅샷은 짧은 TTL 안에서 최근 성공 결과를 먼저 다시 씁니다. 새 캐시는 데이터 소스 우선순위 전체를 순서대로 기록하며, 현재 우선순위가 기록 당시와 같을 때만 다시 씁니다. 그래서 같은 소스 순서 안에서는 대체 소스 결과로 다음 요청을 빠르게 처리할 수 있고, 소스 설정을 바꾸면 실시간 데이터를 다시 읽습니다. 캐시가 만료되면 설정한 우선순위대로 소스를 하나씩 시도하고, 한 소스가 실패하면 다음 소스로 넘어가며 source health와 last-good 캐시를 기록합니다. 현재 Sina, Efinance, AkShare/둥팡차이푸(东方财富, East Money), Tushare 스냅샷 API는 모두 증분 커서나 변경 순서를 제공하지 않습니다. 따라서 TTL 안에서는 요청 없이 다시 쓸 수 있지만, TTL이 지나면 전체 표를 다시 읽어야 합니다. 로컬에서 앞뒤 차이를 비교해도 원본에서 받는 데이터 양은 줄지 않으므로 "증분 수집"이라고 홍보하지 않습니다.
- `TUSHARE_TOKEN`이 있으면 기본으로 Tushare를 먼저 쓰고, 없으면 Sina부터 시작합니다. `SNAPSHOT_SOURCE_PRIORITY`를 명시하면 항상 그것이 우선합니다.
- 일봉은 요청 단위 fetcher로 DSA 과거 시세 흐름을 먼저 다시 쓰고, 결과가 없을 때만 선별 엔진의 대체 데이터 소스로 넘어갑니다. 이 연결은 프로세스 전체의 함수를 바꾸지 않으므로, 동시에 실행되는 선별 요청끼리 wrapper를 공유하거나 서로를 막지 않습니다.
- 사용할 수 있는 LLM 설정이 있으면, 재정렬 전에 스냅샷 점수 상위 3개 후보에 DSA 시세, 기본적 분석, 뉴스와 이벤트(종류별 검색 최대 3건)를 보충합니다. 이벤트 위험이 기존 LLM `risk/risk_flags`와 이후 위험 점수에 반영될 수 있게 하기 위해서입니다. 팩터만으로 정렬할 때는 계속 `pre_rank_light`를 쓰며, 뉴스와 이벤트는 명단이 정해진 뒤에 가져옵니다. 키워드로 탈락시키거나 위험 기준값을 새로 만들지 않습니다.
- 프롬프트에 들어가는 뉴스/이벤트 근거에는 길이가 제한된 제목, 요약, 출처, 링크가 들어가며, 기존 원래 게시 시각과 검색 시각을 유지합니다. 검색 어댑터는 원본 결과의 `retrieved_at`을 그대로 정렬, 최종 응답, 실행 기록까지 전달합니다. 시각 필드가 없으면 알 수 없음으로 두며, 어댑터 처리나 캐시 읽기 시각으로 검색 시각을 지어내지 않습니다. 실제 검색 결과 모델에는 비어 있을 수 있는 `retrieved_at`이 있습니다. 공급자 조회가 실제로 성공하면 UTC 기준 검색 완료 시각을 기록하고, 이후 날짜 정규화, 필터링, 관련도 정렬, 캐시 재사용에서도 원래 값을 유지합니다. 이미 있는 시각은 덮어쓰지 않으며, 시각이 없는 예전 결과는 계속 알 수 없음입니다. 검색 시각은 이벤트가 일어나거나 게시된 시각이 아닙니다. 수집하지 않음, 결과 없음, 조회 실패는 위험이 없다는 뜻이 아니며, 모델은 근거가 부족한 것과 실제 위험을 구분해야 합니다. 기존 프롬프트 길이 예산 때문에 근거가 줄어들 수 있으며, 이 경우 잘라 낸 내용을 설명으로 남깁니다.
- 시장 컨텍스트와 후보 자료(이름, 요약, 뉴스, 이벤트, 링크 포함)는 신뢰할 수 없는 JSON 데이터로 전달됩니다. 별도의 system 메시지가 그 안에 들어 있는 정렬 명령이나 위조된 지시를 따르지 말라고 모델에 요구합니다. 직접 호출, 채널, Router, 대체 모델, 파라미터 복구 모두 같은 경계를 씁니다. 길이 예산에는 system 메시지와 적용 범위 재시도 안내가 포함되며, 잘라 낼 때 외부 데이터의 JSON 경계를 끊지 않습니다. 예산이 부족하면 기존 적용 범위 보호 장치가 기능을 낮춥니다. 이 조치는 프롬프트 주입 위험을 줄일 뿐, 모델이 모든 악의적인 내용을 반드시 무시한다고 보장하지는 않습니다. 후보 코드 허용 목록과 구조화 출력 검증은 계속 적용됩니다.
- `pre_rank_research`의 전체 결과는 선별 호출 한 번 안에서 다시 씁니다. 선정된 후보에 대해서는 이미 시도한 뉴스/이벤트(빈 결과, 게시 시각 불명, 실패 결과 포함)를 다시 조회하지 않습니다. 다음 실행에서는 검색 서비스의 기존 캐시와 대체 흐름을 다시 거칩니다. 재정렬 뒤 새로 선정되었는데 미리 조회하지 않은 후보는 원래의 선정 후 보강 상한(선정 후보 상위 3개)대로 보충합니다. 한 번의 실행에서 최대로 다루는 후보는 재정렬 전 3개와 선정 후 3개, 서로 다른 후보까지입니다. 검색 지연이 앞쪽으로 옮겨올 수 있으며, 소스 하나가 실패해도 선별은 멈추지 않습니다.
- 이 개선은 제한된 후보의 이벤트 근거를 LLM 정렬에 반영하는 것일 뿐, 전체 시장 이벤트 필수 필터나 확정된 자동 이벤트 위험 관리가 아닙니다. LLM을 쓸 수 없으면 원래 팩터 정렬과 기능 저하 안내를 유지하며, 팩터 모드는 사후 검색 결과로 명단을 고치지 않습니다.
- 기본 로컬 `scorecard`는 짧은 후보 목록 전체를 다룹니다. 그래서 비슷한 점수 교체에 들어갈 수 있는 모든 후보가 같은 최종 점수 기준을 씁니다. 여러 사후 분석기를 이어서 실행하면 각 단계가 끝날 때마다 최신 점수로 다시 정렬하므로, 이후 `dsa`와 `external_http`의 `POST_ANALYSIS_MAX_PICKS` 상한은 현재 실제 상위권에 적용됩니다. 원격 상태는 실제로 보낸 후보 기준으로 기록하며, 외부 응답에 상한을 넘는 코드가 있어도 보내지 않은 후보는 바뀌지 않습니다. 원격 분석을 켜면 교체는 같은 분석을 마친 후보끼리만 일어납니다.
- 모델, 채널, base URL, 추가 headers, fallback, timeout, token 상한은 호출 한 번의 범위에서만 주입되며 사용자 설정을 고치지 않습니다. 주 모델이 HTTP 호출에는 성공했어도 빈 내용, JSON이 아닌 응답, 적용 범위 부족을 반환하면 설정된 대체 모델을 계속 시도합니다. 최종 JSON은 `content` 블록이나 `output` 블록에 있어야 합니다. `reasoning_content`(추론 과정)는 내부 보조 정보로 보고 최종 결과로 쓰지 않습니다.
- 테마 순위 새로고침과 긴 선별 흐름은 동시에 실행될 수 있습니다. 목록은 기본적으로 상세 정보를 한꺼번에 미리 가져오지 않으며, 사용자가 특정 테마를 고를 때만 그 테마의 상세 정보를 불러옵니다. 명시적으로 새로고침한 뒤에도 현재 테마를 계속 보고 있다면, Web은 상세 캐시를 우회해 그 테마를 함께 다시 가져옵니다. 순위와 상세 정보가 같은 새로고침에서 나오도록 하기 위해서입니다.
- 테마 구성 종목은 둥팡차이푸와 퉁화순(同花顺, Tonghuashun) 데이터를 동시에 가져와, 정해진 데이터 소스 우선순위로 합칩니다. 응답 순서 때문에 중복 종목의 필드가 바뀌는 일을 막기 위해서입니다. 양수 `SCREENING_HOTSPOT_CALL_TIMEOUT_SEC`는 기본 provider 호출 한 번 전체가 함께 쓰는 예산이며, 업종 목록, 구성 종목, 엔진 실패 후 직접 상세 조회 fallback이 모두 이 예산 안에 들어갑니다. AkShare/둥팡차이푸의 종료 가능한 하위 프로세스와 퉁화순 HTTP connect/read timeout은 단계마다 남은 시간만 쓰며, fallback이 예산 전체를 새로 받지 않습니다. 직접 상세 조회 fallback은 이 예산으로 강제로 회수할 수 없는 실시간 시세 사전 조회를 따로 시작하지 않으며, 시세 필드는 이미 통제된 구성 종목 소스 결과를 기준으로 합니다. 시간을 넘긴 하위 프로세스는 terminate/kill로 종료해 회수합니다. 프로세스 단위 동시 실행 슬롯이 활성 작업 수를 제한하며, 메서드가 끝나기 전에 받아들인 worker가 끝나기를 기다려 백그라운드 스레드를 남기지 않습니다. 호출 전체 예산을 끄면 각 소스는 기본 강제 제한 시간을 유지합니다. 소스 하나가 실패해도 다른 소스와 로컬 핵심 종목 대체 경로는 막히지 않습니다.
- "최신 뉴스 검색"은 DSA 원래 검색 서비스의 provider 우선순위, SearXNG 공개 인스턴스 기능, 결과 캐시, 요청 합치기를 다시 씁니다. 같은 캐시 키에서는 소유자(owner)만 공급자 순서를 시작할 수 있습니다. 소유자가 캐시할 수 있는 결과를 내지 못하면 기다리던 요청이 다시 경쟁하고, 소유권을 얻지 못한 요청은 계속 기다립니다. 다만 캐시 대기, 소유권 경쟁, provider 실행은 요청의 절대 마감 시각을 함께 쓰므로, 줄을 섰다고 제한 시간을 처음부터 다시 받지는 않습니다. 검색은 링크가 있는 이벤트/촉매만 보충하며, 웹페이지 내용으로 업종 구성 종목을 추측하지 않습니다. 보강 기록은 표시용 흐름과 원래 시간순 기록에 각각 덧붙이며, 기존 `timeline`을 덮어쓰지 않습니다. 검색은 사용자가 직접 실행하며, 요약은 로컬에서 정해진 규칙으로 줄이고 LLM을 호출하지 않습니다. 응답은 `available`, `no_results`, `unavailable`로 결과 있음, 정상적인 빈 결과, 시간 초과/용량/공급자 실패를 구분하므로, Web은 더 이상 실행 실패를 "최근 뉴스 없음"으로 안내하지 않습니다. 검색 보강은 이번 응답에만 있으며, 공유 테마 상세 캐시에 기록하거나 유효 기간을 늘리지 않습니다. 기본 상세 요청에는 검색 상태가 보이지 않고 검색 대기 시간도 늘지 않습니다. 공급자 하위 프로세스가 시작, 실행, 정리 중 어느 단계에서 실패해도 프로세스 단위 용량은 반환됩니다.
- 테마 실시간 요청이 실패하면 last-good 캐시를 먼저 씁니다. 캐시가 없으면 일정한 빈 상태와 분명한 오류를 반환합니다.

## 결과 교체

Web은 브라우저 안에서 사용자 정보가 들어 있지 않은 익명 시드(seed)를 만들고, 동기 또는 백그라운드 선별 요청에 `variant_seed`로 함께 보냅니다. Web Storage를 읽거나 쓸 수 없으면 현재 페이지 세션의 모듈 메모리에서 같은 임시 시드를 다시 써, 동기 진입점과 백그라운드 작업 진입점이 같은 값을 쓰도록 합니다. 서버는 익명 시드를 이번 실행 ID, 시장, 전략과 함께 변동 입력으로 씁니다. 그래서 다른 브라우저끼리, 또는 같은 브라우저의 다른 실행끼리 품질이 비슷한 후보 가운데 서로 다른 종목을 볼 수 있습니다.

이 변동은 점수를 무작위로 바꾸는 것이 아니며 전략을 우회하지도 않습니다. 필수 필터, 위험 탈락, 팩터/LLM 점수, 최종 점수, 포트폴리오 집중도 감점이 모두 먼저 실행됩니다. 기본 로컬 점수 계산은 짧은 후보 목록 전체를 다룹니다. 개수 상한이 있는 원격 사후 분석을 켜면 같은 분석을 마친 후보만 교체에 참여할 수 있습니다. 분석기가 만든 후보 순서가 교체 입력의 기준 순서이며, 점수가 같아도 종목 코드로 다시 정렬하지 않습니다. 원래 Top-N의 앞쪽 절반과 마감 점수보다 분명히 높은 후보는 항상 보호됩니다. 뒤쪽 절반 자리만, 원래 마감 점수보다 1.5점 이상 낮지 않은 비슷한 점수 후보 풀에서 뽑으며, 선정된 후보는 입력의 상대 순서를 계속 유지합니다. 시드는 선별 결과나 실행 기록에 저장되지 않습니다. `variant_seed`를 넘기지 않거나 교체 비율을 0으로 두면 입력 그대로의 Top-N을 반환해 스크립트와 예전 클라이언트와의 호환을 유지합니다.

| DSA 기본적 분석/자금 흐름 | `DataFetcherManager`의 기본적 분석 캐시 | 기본 TTL 120초. `FUNDAMENTAL_CACHE_TTL_SECONDS`를 따름 |
| DSA 뉴스/공시 이벤트 | `SearchService` 메모리 캐시 | 성공 결과는 기본 TTL 10분. 같은 테마의 동시 요청은 부모 프로세스에서 합치고, 실제 공급자 호출은 속도 제한이 있는 종료 가능한 하위 프로세스에서 실행. 서비스를 다시 시작하면 새로 조회 |
| 전체 선별 결과 | DSA 데이터베이스 `screening_runs` 테이블 | 완료 후 `run_id` 기준으로 중복 없이(멱등) 기록. 데이터베이스 기록에 실패해도 선별 주 흐름은 멈추지 않음 |

후보 컨텍스트 모듈도 24시간 파일 캐시를 지원하지만, DSA 연동에서는 그 모듈의 독자적인 뉴스/공시 수집을 기본으로 끄고 DSA 자체의 뉴스, 기본적 분석, 실시간 시세 흐름을 씁니다. 같은 후보에 대해 두 데이터 소스 묶음으로 중복 요청하는 일을 막기 위해서입니다.

### 일봉의 최신성

- 기존 거래일 달력과 시장 시간대를 다시 씁니다. 장 시작 전에는 직전에 마감된 거래일만 받아들이고, 장중에는 최소한 직전에 마감된 거래일까지 있어야 하며 마지막 날짜가 실제 거래일이어야 합니다. 장 마감 후에는 당일까지 있어야 합니다. 주말과 휴일에는 가장 최근에 마감된 거래일까지 있어야 합니다. 다시 장이 열린 뒤 장중에도 날짜 범위 안에 휴장일의 가짜 일봉이 있으면 거부합니다. TTL은 여전히 별도의 상한이며, 휴장이라고 TTL이 자동으로 늘어나지 않습니다.
- 장 마감 전에 만들어진 캐시 파일은 당일의 일부 캔들을 담고 있더라도 장 마감 후 완전한 일봉으로 볼 수 없습니다. 캐시가 다루는 날짜가 부족하거나, 날짜가 없거나 잘못되었거나, 날짜가 현재 시장 날짜보다 미래이거나, 마지막 날짜에 유효한 종가가 없으면 TTL 안이라도 새로 가져오기를 시도합니다.
- DSA 일봉도 다루는 날짜를 확인하고 기존 오래됨(stale) 표시를 유지합니다. 오래된 DSA 데이터는 먼저 선별 엔진 자체 데이터 소스를 시도합니다. 자체 소스에서 최신 일봉을 얻으면 바꾸고, 모든 소스가 오래되었으면 가장 최근의 유효한 날짜를 고릅니다. 날짜가 같으면 DSA 우선순위를 유지하며, 대체 소스의 실패와 기능 저하 정보를 기록합니다. DSA와 자체 소스의 오래된 일봉은 모두 last-good 파일 캐시를 덮어쓰지 않습니다. 호출하는 쪽이 넣은 예전 일봉도 오래됨으로 표시합니다.
- `DAILY_SOURCE=auto`에서 비어 있지 않은 오래된 결과가 나와도 소스 순서는 끝나지 않으며, 기존 순서대로 다음 소스를 계속 시도합니다. 최신 결과를 얻어야만 캐시를 갱신합니다. 어떤 소스도 최신 일봉을 주지 못하면, 실시간으로 받은 모든 오래된 결과와 파일 캐시의 마지막 유효 일봉 날짜를 비교해 날짜가 더 가까운 데이터를 먼저 씁니다. 날짜가 같으면 원래 소스 우선순위를 유지합니다. 캐시에 있는 장중 데이터는 계속 오래됨으로 표시하며, 완전한 종가 데이터 행세를 하지 않습니다. 오래된 소스는 소스 순서 설명에 기록되고, 실제 요청 실패는 계속 `source_errors`에 기록됩니다. 최신 대체 결과는 오래됨 표시를 물려받지 않습니다.
- 파일 캐시는 데이터 안에 들어 있는 시간대 포함 수집 시각으로 TTL과 장 마감 전환을 먼저 판단합니다. 데스크톱 백업을 복원해 파일 수정 시각(mtime)이 바뀌어도 이런 캐시의 수집 시각은 새로 고쳐지지 않습니다. 예전 형식의 시간대 없는 `created_at`은 원래 기록한 컴퓨터의 시간대를 알 수 없으므로, 시각이 없거나 잘못된 캐시처럼 mtime을 대신 씁니다. 다른 컴퓨터로 옮길 때는 파일 mtime을 유지하세요. 유효한 종가가 있는 모든 날짜 행은 실제 거래일인지 확인합니다. 자체 소스, DSA, 캐시에 섞인 주말, 휴일, 날짜가 없거나 해석할 수 없는 bar도, 마지막 행이 정상 거래일이더라도 거부합니다. 유효한 종가가 없는 행은 이 확인에 포함하지 않습니다.
- `DAILY_SOURCE=yfinance`를 명시하면 미국 동부 시장 날짜로 일봉 다운로드 범위를 정하고, 끝을 포함하지 않는 `end`를 다음 날로 둡니다. UTC나 미국 동부 등 어떤 배포 시간대에서도 장 마감 후 공급자가 이미 제공한 당일 캔들을 받을 수 있게 하기 위해서입니다.
- 오래된 데이터는 `daily_stale` / `daily_quality_flags=stale_cache` 기능 저하 계약을 그대로 따르며, 기존 일봉 품질 점수와 위험 감점에 반영됩니다. 데이터 소스 장애가 선별 작업 전체의 실패로 이어지지 않습니다. 최신성 검사는 전략의 필수 필터, 위험 탈락 스위치, 팩터 가중치를 바꾸지 않습니다.
- 달력을 쓸 수 없거나, 시장을 알 수 없거나, 달력 범위가 부족하면 TTL 판단을 유지합니다. 명시적인 오래됨 표시는 계속 유효합니다. 날짜 범위 검사는 기록이 뒤처졌는지만 확인할 수 있을 뿐, 공급자의 당일 캔들이 정산을 마쳤는지는 증명할 수 없습니다. 공급자 수집 시각이 없는 당일 데이터에는 이 한계가 그대로 남습니다.

선별 실행 기록은 현재 명단 재현과 진단에 쓰입니다. 기존 `BacktestService`의 후보는 개별 종목 분석 기록에서 오며, `screening_runs`를 직접 평가하지는 않습니다. 선별 실행 단위로 T+N(N거래일 뒤) 평가를 하려면 기존 백테스트 흐름에 연결해야 하며, 전략 메타데이터를 저장했다고 수익 검증이 끝난 것은 아닙니다.

## 두 종류 전략의 경계

DSA에는 용도가 다른 두 종류의 전략 파일이 있습니다.

| 위치 | 해결하는 문제 | 불러오는 곳 | 실행 단계 |
| --- | --- | --- | --- |
| `src/services/screening/strategies/*.yaml` | 전체 시장에서 어떤 후보를 고를지 | `src/services/screening/strategy.py` | 스냅샷 필터, 팩터 점수, 위험, 정렬 |
| `strategies/*.yaml` | 종목 하나를 어떻게 분석하고 결론을 낼지 | `src/agent/skills/base.py` | DSA Agent/보고서 분석 |

`shrink_pullback`, `volume_breakout`처럼 이름이 같아도 두 종류는 다른 폴더, Schema, loader를 쓰므로 서로 덮어쓰지 않습니다. 선별 전략은 `analysis_skills`로 다음 단계에 쓸 것을 권하는 분석 skill을 선언할 수 있으며, Web의 "심층 분석 이어서 하기"는 이 skill을 명시적으로 함께 넘깁니다. 대응 관계를 선언하지 않은 선별 전략은 사용자가 현재 고른 분석 전략이나 기본 분석 전략을 계속 쓰며, 의미가 확실하지 않은 대응을 억지로 만들지 않습니다.

## DSA 기본 기능 재사용

- 시세: 일봉은 DSA `DataFetcherManager`를 먼저 부르고, 결과가 없을 때만 선별 모듈 자체의 다중 소스 fallback으로 넘어갑니다. 최종 후보에는 계속 DSA 실시간 시세를 보충합니다.
- 기본적 분석과 뉴스: 최종 후보는 DSA 기본적 분석 컨텍스트와 `SearchService`를 다시 씁니다. 자금 흐름은 DSA 기본적 분석 컨텍스트에서 오고, 주요 공시/실적/지분 매도 이벤트는 DSA `search_stock_events`를 호출합니다. 테마 뉴스 검색은 그 데이터 소스 우선순위, 시효 필터, 캐시, 같은 요청 합치기를 그대로 쓰며, 실제 공급자 호출만 종료 가능한 하위 프로세스로 분리합니다. 별도의 뉴스 진입점을 중복으로 관리하지 않습니다.
- 모델: DSA LiteLLM의 모델, 채널, fallback, base URL, 추가 headers, 제한 시간, token 설정을 그대로 씁니다.
- 작업과 화면: DSA 백그라운드 작업 큐, Web 조회, 데스크톱 앱의 같은 출처 Web 리소스를 다시 씁니다.
- 저장과 후속 분석: 실행 결과는 DSA 데이터베이스에 기록되며, 후보는 전략 skill을 들고 DSA 기본 개별 종목 분석으로 넘어갈 수 있습니다.

고정된 참고 커밋과 비교하면 스냅샷, 일봉, 미국 주식, 업종/테마, 핫스팟, 후보 뉴스/공시/자금 흐름, 필드 표준화, 필터, 점수, 위험, 정렬, 데이터 소스 차단기 등 원본 데이터와 선별 기능은 모두 들어왔습니다. 그중 공시/이벤트와 자금 흐름은 DSA 흐름 구성 계층에서 각각 기본 이벤트 검색과 기본적 분석 컨텍스트에 연결했습니다. 참고 프로젝트는 별도의 CLI/server, JSON 파일 저장소, 보고서 렌더링, doctor, 실행/데이터 소스 기록, T+N 평가도 제공합니다. 이 구현은 DSA에 정말 없던 실행 기록과 데이터 소스 기록만 받아들여 DSA 데이터베이스에 연결했으며, CLI/server는 중복으로 만들지 않습니다. 이후 선별 T+N 평가는 두 번째 백테스트 기준이 생기지 않도록 DSA의 기존 BacktestService에 연결해야 합니다. 현재 이 서비스는 개별 종목 분석 기록을 평가합니다. 실시간 source health는 이미 `/status`에서 반환하고, 과거 안정성은 `/source-history`가 보완합니다.

## 얻는 점

1. 선별 서비스, 전략, API, Web, 패키징 스크립트가 같은 버전 안에서 함께 바뀌므로 계약이 어긋나지 않습니다.
2. 서비스 계층에는 기본 호출 경로가 하나뿐이어서, 상태 점검과 실제 요청이 같은 구현을 반영합니다.
3. Docker와 데스크톱 결과물이 같은 모듈과 전략 리소스를 바로 담으므로 배포 결과가 더 일관됩니다.
4. 데이터 소스 대체, 점수, 전략 변경을 본 저장소에서 처음부터 끝까지 검토하고 회귀 테스트할 수 있습니다.
5. 출처 커밋, 라이선스, 파일별 귀속이 분명해 이후 원본 수정 사항을 골라서 가져오기 쉽습니다.

| 데이터 소스 요청 제한이나 필드 변경 | 스냅샷, 테마, 일봉 기능 저하 | timeout, retry, source health, last-good 캐시 |
| LLM 시간 초과나 형식 오류 | 재정렬을 쓸 수 없거나 설명 필드 누락 | 구조화되지 않은 응답이면 대체 모델을 계속 시도. 모두 실패하면 팩터 정렬을 유지하고 시도한 모델과 실패 이유를 반환 |
| 결과 교체로 후보 차이 확대 | 경계선 후보가 브라우저에 따라 달라질 수 있음 | 비슷한 점수의 뒤쪽 자리만 교체하고, 필수 필터, 위험 탈락, 점수, 상위 후보는 그대로 둠. 시드가 없으면 끔 |
| 캐시 폴더 변경 | 업그레이드 후 예전 캐시를 자동으로 다시 쓰지 않음 | 새 폴더는 `data/screening`으로 분리. 업그레이드 전 필요하면 백업 |
| 실행 기록 증가 | 전체 후보 결과가 데이터베이스 용량을 늘림 | 기록 엔드포인트는 기본적으로 요약만 읽음. 운영자는 기존 데이터베이스 백업/보관 정책으로 관리 가능 |
| 설정과 API 이름 변경 | 기존 자동화도 함께 고쳐야 함 | 릴리스 노트에 `SCREENING_ENABLED`와 `/api/v1/screening`을 분명히 적음 |
| 라이선스 귀속 누락 | 배포 시 규정 준수 위험 | LICENSE, THIRD_PARTY_NOTICES, 파생 파일 머리말 유지 |

선별 결과는 연구와 판단 보조용일 뿐, 투자 권유가 아니며 수익이나 데이터 완전성을 보장하지 않습니다.

## 참고 구현 업데이트

AlphaSift는 참고 출처이지 자동 동기화 대상이 아닙니다. 업데이트할 때는 다음을 지키세요.

1. 대상 커밋과 라이선스 변경을 기록합니다.
2. `src/services/screening/`에 있는 DSA 고유의 수정 사항을 비교하고 모듈별로 골라서 옮깁니다.
3. 파생 파일 머리말, `REFERENCE_REVISION`, `THIRD_PARTY_NOTICES.md`를 고칩니다.
4. pipeline, API/Web 필드, 데이터 소스 대체, 전략 리소스, 묶음 실행 파일 패키징을 확인합니다.
5. 이 문서와 `docs/CHANGELOG.md`를 고치고 백엔드, Web, Docker/데스크톱 검증을 마칩니다.

## 되돌리기

- 기능 되돌리기: `SCREENING_ENABLED=false`로 두고 다시 시작합니다. 일반 개별 종목 분석, 보고서, 알림, 종목 질문에는 영향이 없습니다.
- 코드 되돌리기: 선별 엔진을 들여온 커밋을 revert하고 백엔드, Docker, 데스크톱 결과물을 다시 빌드합니다.
- 데이터 되돌리기: 선별 캐시와 실행 기록을 남기고 싶다면 먼저 `data/screening/`과 DSA 데이터베이스를 백업하세요. 코드를 되돌려도 `screening_runs` 사용자 데이터는 지워지지 않습니다.

실제 실행 메타데이터 `effective_factor_weights`에는 유한하고 음수가 아닌 가중치가 남으며, 명시적으로 0인 비활성 팩터도 포함됩니다. 후보 설명은 양수 가중치만 써서, 비활성 팩터가 선정 이유로 쓰이지 않게 합니다.

장 시작 전에는 직전에 마감된 거래일만 받아들이며, 장 시작 전에 가져온 당일 자리 채움 캔들은 장중에 다시 가져와야 합니다. DSA와 대체 소스가 모두 오래되었으면 마찬가지로 더 최근의 유효한 날짜를 우선하고, 날짜가 같으면 DSA 우선순위를 유지합니다.

모든 소스가 기능을 낮춘 상태에서 비교할 때는 미래가 아니고 실제 거래일인 최신 일봉만 인정합니다. 잘못된 날짜는 유효한 오래된 일봉보다 우선순위가 낮습니다. 달력을 쓸 수 없으면 기존 기능 저하 방식을 유지합니다.

잘못된 날짜나 장 시작 전 자리 채움 데이터만 있고 정상적인 대체 시세가 없으면, 기존의 통합 조회 실패 경로를 거치며 가짜 거래일로 기술 지표 팩터를 만들지 않습니다. DSA와 파일 캐시도 똑같이 검증합니다.

일봉은 거래 날짜 검증을 통과해야 소스 성공으로 칩니다. 잘못된 날짜 응답은 기존 실패 횟수와 차단기에 누적되고, 대기 시간이 지난 뒤 정상 응답이 오면 회복됩니다. 정상적인 오래된 시세는 계속 성공한 조회로 보되 오래된 품질로 처리합니다.
